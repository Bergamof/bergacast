# CI/CD de Bergacast

Détail de `.github/workflows/ci.yml` et `release.yml` (résumé dans `CLAUDE.md`). À lire avant de toucher à la CI, aux scripts `.github/scripts/` ou à la release.

- `.github/workflows/ci.yml` : sur chaque PR (`opened`, `synchronize`, `reopened`, `ready_for_review`, `edited`) → `pr-title` (Conventional Commits, `.github/scripts/check-pr-title.sh`), `release-scripts` (ShellCheck + bats), `backend-lint`, `backend-test`, `backend-build`, `openapi-lint` (Spectral 6.17.0, `.spectral.yaml`, `--fail-severity=warn`), `frontend-lint` (Prettier, ESLint, svelte-check), `frontend-test`, `frontend-build`, `backend-dependencies` (Trivy sur le jar, transmis par `backend-build` en artefact), `frontend-dependencies` (`npm audit --audit-level=high`, dépendances de dev comprises), `secrets` (gitleaks, tout l’historique, `.gitleaksignore`), `codeql` (Java sans build, TypeScript, workflows ; `security-extended` ; alertes listées dans le log ; un résultat haut/critique bloque tant que l’API code scanning le dit ouvert ; sur une PR, l’API ne suit que les alertes des fichiers modifiés, les autres sont jugées sur `main`, où tout résultat haut doit être connu de l’API (inconnu = bloquant) ; un faux positif est écarté dans GitHub par Adrien, jamais exclu dans le dépôt), `frontend-lighthouse` (`frontend/lighthouserc.json`, API simulée `frontend/lighthouse/`, ≥ 0,9 Accessibilité et Bonnes pratiques, contrôle que chaque page a chargé ses données ; puis parcours `frontend/e2e/` : focus, statuts, reprises 412/503, page d’erreur, axe-core sans violation en clair et sombre, 320 px), `backend-image` (image native + services Postgres et S3Mock + `smoke-test.sh`, taille et mémoire, Trivy), `frontend-image` (image + vérifs de service, Trivy), `migration-check` (Spotless, Checkstyle, tests), `migration-image` (image lancée deux fois sur PostgreSQL, Trivy), `migration-dependencies` (Trivy sur les jars, aussi la nuit) → `report` (`if: always()`) qui commente la PR.
- Aussi sur push `main` (sans `report`) et chaque nuit sur `main` (`schedule` : seuls `backend-build`, `backend-dependencies`, `frontend-dependencies`, `migration-dependencies`, `secrets`, `frontend-image` ; les autres jobs portent `if: github.event_name != 'schedule'`). Chaque job expose un output `summary` calculé dans une étape `if: always()` ; `report` les agrège (tableau `checks` du script) et met à jour un commentaire unique repéré par `<!-- bergacast-ci-report -->`. Toute nouvelle vérification est ajoutée à la CI, aux `needs` de `report` ET à son tableau `checks`.
- Protection de `main` recommandée : les 19 jobs de vérification obligatoires.
- Sécurité de la chaîne : actions épinglées par SHA (`# vX.Y.Z`, Dependabot) ; images Docker épinglées par empreinte (Dependabot `docker` pour les Dockerfile et `docker-compose` pour `compose.yaml` met à jour tag et empreinte, majeures de `node`, `eclipse-temurin`, GraalVM et `postgres` ignorées : montée à la main ; les `services` de `ci.yml` et les images Testcontainers ne sont pas suivis par Dependabot : à reporter à la main) ; Trivy et gitleaks installés depuis leurs releases avec SHA-256 épinglé (pas d’action tierce : tags de `trivy-action` réécrits en mars 2026) ; scan Trivy partagé dans l’action composite `.github/actions/trivy-scan` (échec sur CRITICAL/HIGH, exceptions justifiées et datées dans `.trivyignore.yaml`, vide par défaut).
- `.github/workflows/release.yml` : `workflow_dispatch` seul, depuis `main` (une release à la fois) → `ci` (`wait-for-ci.sh` : CI du push du commit de tête de `main` attendue puis exigée verte) → `plan` (`.github/scripts/release-plan.sh` : modules `backend`/`frontend`/`migration` modifiés depuis le dernier tag `vX.Y.Z`, aucun → arrêt ; `!`/`BREAKING CHANGE` → majeure, `feat` → mineure, sinon patch, sur tous les commits depuis ce tag) → `publish` (matrice des modules modifiés, `build-args: VERSION`, tags `X.Y.Z`, `X.Y`, `X`, `latest`, `sha-<court>`, `linux/amd64`, secret `SCW_SECRET_KEY`, login `nologin`, cache `type=gha,scope=<module>-image` partagé avec la CI) → `migrate` (`run-migration-job.sh`, si l’image de migration est publiée : définition du job mise à jour, run attendu, doit réussir) → `deploy-backend` puis `deploy-frontend` (`deploy-container.sh` : conteneur mis sur la nouvelle image, attendu `ready` ; seulement les modules publiés ; environnement GitHub `production` : secret `SCW_DEPLOY_SECRET_KEY`, variables `SCW_JOB_DEFINITION_ID`, `SCW_BACKEND_CONTAINER_ID`, `SCW_FRONTEND_CONTAINER_ID`, `SCW_REGION`) → `tag` (tag + release GitHub via `gh`, notes `.github/scripts/release-notes.sh`), posé après les déploiements : relancer le run rejoue la même version. Appels à l’API Scaleway en curl + jq (`scaleway.bash` : jobs `v1alpha2`, containers `v1`), sans binaire `scw`.
- `main` est protégé (19 vérifications obligatoires, branche à jour exigée, administrateurs inclus) : chaque PR mergée met les autres en retard ; les merger une par une, mettre à jour la branche (`update_pull_request_branch`) puis attendre la CI.
- `frontend-dependencies` : `npm audit` complet (dev compris) puis `.github/scripts/npm-audit-gate.sh` ; les exceptions acceptées sont dans `frontend/npm-audit-exceptions.json` (voir `decisions.md`, 2026-11-17).
