# Bergacast
Service auto-hébergé de publication de podcasts : des outils automatisés publient des épisodes (audio + métadonnées) via une API authentifiée par podcast ; métadonnées dans PostgreSQL ; audio, image de couverture (réduite à 3000 px) et flux RSS sont des objets publics d’un stockage objet S3 (Scaleway Object Storage), clé = chemin de l’URL publique (`{slug}.xml`, `{slug}/image.{ext}`, `{slug}/episodes/{id}/audio.{ext}`), retrouvables sans la base ; le flux est réécrit à chaque modification ; une SPA d’administration gère le tout. Production : deux images (backend natif GraalVM, frontend statique) sur Scaleway Serverless Containers. Dépôt : github.com/Bergamof/bergacast, branche principale `main`.

## Méthode de travail
- Tâche non triviale : d'abord un plan d'action (choix techniques et fonctionnels justifiés, étapes, livrables, spécialistes mobilisés, risques), puis attendre le « go » d'Adrien avant de coder. Écart significatif en cours de route → resoumettre.
- Seul le chef écrit, sur tout le dépôt ; il travaille en expert de chaque techno du projet et de la CI/CD, en vérifiant la documentation officielle. Aucun agent d'écriture n'est créé, même pour une nouvelle techno. Pas de spécialiste pour une micro-tâche.
- Boucle : le chef développe → rapports des seuls spécialistes concernés (en parallèle, briefs autosuffisants) → le chef suit leurs recommandations et corrige → nouvelle passe ciblée, jusqu'à zéro bloquant/majeur ; mineurs non traités listés à Adrien. Recommandation contestable : le chef tranche et justifie ; enjeu significatif → Adrien.
- Réutiliser les spécialistes existants ; jamais de suppression d'agent sans accord d'Adrien. Piège appris → enrichir la définition du spécialiste dans le même commit.
## Définition de « done » (sauf indication contraire d'Adrien)
- Terminé seulement quand toutes les CI déclenchées par les modifications sont vertes sur le dernier commit poussé. Des tests locaux verts ne suffisent pas.
- Après chaque push / ouverture de PR : suivre les runs jusqu'à la fin. Échec : lire les logs, corriger la cause racine (le chef), repousser, re-surveiller.
- Interdit pour obtenir le vert, sauf accord explicite d'Adrien : skipper/désactiver un test, assouplir le lint, `continue-on-error`, supprimer un job, baisser un seuil (couverture, Lighthouse, sévérité CVE).
- Échec non lié (flaky, infra, service externe) : relancer une fois, puis signaler avec le diagnostic. Après ~3 échecs sur le même problème : s'arrêter et exposer diagnostic et pistes.
- CI inaccessible : annoncer « terminé localement, CI non vérifiée », jamais « done ».
- CI verte : annoncer la fin avec le lien du run, puis arrêter de surveiller la PR (pas d'attente des commentaires/reviews, sauf demande).

## Architecture
- Backend package-by-feature `fr.bergadev.bergacast` :
  - `podcast` (événements `PodcastFeedChanged`/`PodcastDeleted` publiés dans la transaction ; image du podcast dans `PodcastImage*` : métadonnées en base, contenu dans le bucket), `episode` (`EpisodePublication` : audio envoyé hors transaction puis épisode enregistré, objet supprimé si l’enregistrement échoue ; `EpisodeMetadataReader`), `audio` (`AudioUploads` : SHA-256 puis `PutObject`), `token` (jetons d’API), `adminuser` ;
  - `storage` (`StorageConfiguration` : `S3Client` path-style, checksums `WHEN_REQUIRED` ; `ObjectStorage` put/delete/`discard` (échec journalisé, orphelin) ; `MediaKeys` : clés = chemins publics ; `AfterCommit` : effets sur le stockage après commit ; `PodcastObjectsCleanup`) ;
  - `image` (`ImageResizer` : contrôle du format réel, plafond 50 Mpx lu dans l’en-tête avant décodage, réduction à 3000 px max, sinon octets d’origine intacts) ;
  - `feed` (`FeedEpisodeSelector` pur + `RssFeedWriter` ; `FeedPublisher` écoute `PodcastFeedChanged` et écrit `{slug}.xml` après commit, transaction `REQUIRES_NEW`, verrou par podcast dans le processus ; échec → `FeedPublicationException` → `503`) ;
  - `security` (chaîne de filtres, JWT, handler Problem Details, CORS, `LoginThrottle` : limitation des connexions par identifiant, en mémoire), `web` (Problem Details, ETags, liens, racine, `/error`, `MediaRedirectController`, `JsonRequestSizeFilter` : corps JSON ≤ 256 Kio, `RobotsHeaders` : `X-Robots-Tag` posé sur toute réponse par `SecurityConfiguration` ; `PublicUrls` : API sur `public-base-url`, médias sur `media-base-url`) ;
  - `requestlog` (`RequestLogFilter` : une ligne INFO par requête `GET /x.xml 404 3ms db=yes ua="…"`, sans query string/en-têtes/IP, sondes `/actuator/health/{liveness,readiness}` non journalisées (`/actuator/health` l’est : il interroge la base) ; `db` vient de `ConnectionTrackingDataSource`, enveloppe de la `DataSource` posée par `ConnectionTrackingPostProcessor`, suivi par thread dans `ConnectionUsage`) ;
  - `config` (`BergacastProperties`, `OpenApiConfiguration` + `OpenApiConventions`, `Clock`, `MultipartConfiguration`, `NativeImageHintsConfiguration` + `ImageProcessingHints` : hints GraalVM manquants).
- Migrations : module `migration/` (Liquibase, `MigrationMain` lit `BERGACAST_DATASOURCE_URL/USERNAME/PASSWORD`, `Migrator`, `DatabaseSettings`) ; *changelog* `src/main/resources/db/changelog/db.changelog-master.yaml` + `changes/` (`0001` schéma de référence = ancien Flyway V1–V4, noté `MARK_RAN` sur une base déjà migrée, `0002` supprime `flyway_schema_history`) ; image lancée comme job Scaleway avant le redéploiement du backend, donc migrations compatibles avec le backend précédent (ajouter, supprimer à la release suivante). Backend : `ddl-auto: none`, `spring.jpa.database: postgresql`, `allow_jdbc_metadata_access: false`, aucune migration ; ses tests construisent le schéma avec le module (`includeBuild("../migration")` dans `settings.gradle.kts`, seulement si le dossier existe : le Docker du backend n’a que `backend/`) et gardent `ddl-auto: validate` (annotation `IntegrationTest`).
- Tests : `backend/src/test/...` (package miroir) ; `support/IntegrationTest` + `TestcontainersConfiguration` (postgres:18 + S3Mock, bucket `bergacast`) + `ApiTestClient` + `StoredObjects` (lecture des objets du bucket) ; `config/OpenApiSpecExportTest` alimente `generateOpenApiSpec`.
- Release : `.github/scripts/` (`release-plan.sh`, `release-notes.sh`, `check-pr-title.sh`, `wait-for-ci.sh`, `run-migration-job.sh`, `deploy-container.sh`, `scaleway.bash`, classification partagée `conventional-commits.bash`, tests bats dans `tests/` avec `stub_command` pour `gh` et `curl`).

## Modèle de domaine
- **Podcast** : id uuid, slug (unique, immuable, `^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 64, réservés dans `podcast/Slugs`), title*, description*, author, ownerName, ownerEmail, language* (BCP-47), category, explicit, imageUrl, websiteUrl, réglages de flux (`maxEpisodes` ≥ 1 ou null, `evictOldestBy`, `sortBy` ∈ `PUBLICATION_DATE|ADDED_DATE`, `sortDirection` ∈ `DESC|ASC`, `includeFutureEpisodes`), createdAt, updatedAt, version.
- **Episode** : id, podcast, guid (unique par podcast, défaut UUID), title*, description, publicationDate (défaut maintenant), addedAt, durationSeconds, season, episodeNumber, episodeType (`FULL|TRAILER|BONUS`), explicit (nullable), audioFile (1:1), idempotencyKey (unique par podcast), version.
- **PodcastImage** : podcast_id (PK, FK `ON DELETE CASCADE`), mimeType (`image/jpeg|png`), width, height, sizeBytes, sha256 ; contenu : objet `{slug}/image.{jpg|png}`. Ajout/remplacement/suppression → incrémente la `version` du podcast. Flux : `itunes:image` = image envoyée, sinon `imageUrl` (externe), sinon rien.
- **AudioFile** : id, mimeType, sizeBytes, sha256, fileExtension ; contenu : objet `{slug}/episodes/{episodeId}/audio.{ext}` (id d’épisode attribué par l’application avant l’envoi).
- **ApiToken** : id, podcast, name, tokenHash (SHA-256, unique), tokenPrefix (8 car.), createdAt, lastUsedAt ; format `bgc_` + 32 octets base64url, montré une seule fois.
- **AdminUser** : id, username unique, passwordHash (encodeur délégant), createdAt ; mot de passe ≥ 12 caractères.
- Flux (calculé à chaque écriture) : tous les épisodes → sans `includeFutureEpisodes`, `publicationDate <= now` → si `maxEpisodes`, garder les N plus récents selon `evictOldestBy` → tri `sortBy`/`sortDirection` (départage : autre date, puis id).
- Cascades : suppression podcast → épisodes et jetons (FK `ON DELETE CASCADE`) puis, après commit, objets `{slug}.xml` et `{slug}/*` ; trigger : suppression épisode → `audio_file` ; objet audio supprimé après commit.

## Pièges et conventions spécifiques
- Administrateur initial : créé par le job de migration (`InitialAdministrator` lit `BERGACAST_ADMIN_USERNAME/PASSWORD`, `AdministratorAccounts.createIfNone` : `INSERT … WHERE NOT EXISTS`, hash `{bcrypt}` du même encodeur délégant que le backend), jamais par le backend ; `TestcontainersConfiguration` appelle `MigrationMain.run` pour migrer et créer l’administrateur des tests ; `StartupWithoutDatabaseTest` démarre le vrai backend sans base.
- Le BOM Spring Boot gère Liquibase 5 (FSL) : `backend/build.gradle.kts` impose `strictly("4.33.0")` à `liquibase-core` pour ses tests (même version que `migration/build.gradle.kts`, un écart fait échouer la résolution) ; vérifier avec `./gradlew dependencyInsight --dependency liquibase-core --configuration testRuntimeClasspath`.
- Migration : `Migrator` encapsule `LiquibaseException`/`UnexpectedLiquibaseException` dans `MigrationFailedException` ; ne jamais modifier un changeset appliqué ; build Docker du module impossible dans le bac à sable (TLS interceptée dans `docker build`) : image vérifiée en CI, exécution vérifiée en copiant `build/install/*/lib` dans une image distroless.
- Natif : une réflexion manquante n’échoue qu’à l’exécution (`MissingReflectionRegistrationError`) → ajouter le hint dans `config/NativeImageHintsConfiguration` (+ test), reconstruire l’image, relancer `smoke-test.sh`. Avertissements Flyway « Unable to scan location … unsupported protocol: resource » au démarrage natif : bénins.
- Natif + ImageIO/AWT : les `.so` JNI émis par native-image (`libawt`, `libawt_headless`, `libjavajpeg`, `liblcms`, `libjava`, `libjvm`) doivent être copiés à côté de l’exécutable (`backend/Dockerfile`, liste explicite ; `libawt_xawt`/`libfontmanager` exclus : X11/freetype absents) + hints JNI dans `config/ImageProcessingHints` (générés avec l’agent de traçage).
- `./gradlew test` exécute aussi `processTestAot` (plugin natif) : démarre chaque contexte de test en AOT.
- Scaleway Serverless SQL (base de prod) : verrous consultatifs « non garantis » (Flyway ; Liquibase n’en utilise pas) ; authentification IAM (utilisateur = ID du principal, mot de passe = secret key d’une clé API de ce principal, permission Serverless SQL requise).
- Scaleway Object Storage : une *bucket policy* ne laisse passer que les principaux listés (y inclure l’application IAM du backend) ; S3 ne peut pas ajouter `X-Robots-Tag`, et un `robots.txt` n’est lu qu’à la racine d’un domaine : seulement avec un domaine dédié aux médias (dépôt manuel unique, README), impossible en path-style.
- `AfterCommit` : une exception levée après commit remonte à l’appelant (transaction déjà validée) et empêche les synchronisations suivantes → enregistrer les nettoyages avant l’écriture du flux. Lire en base depuis un callback après commit exige une nouvelle transaction (`REQUIRES_NEW`).
- `spring.datasource.hikari.*` est en millisecondes (lié aux setters `long` de `HikariConfig`) : `30s` → `NumberFormatException` au démarrage.
- La `DataSource` injectée est l'enveloppe `requestlog/ConnectionTrackingDataSource` : injecter `DataSource` puis `unwrap(HikariDataSource.class)` pour accéder au pool (un `@Autowired HikariDataSource` échoue).
- Bac à sable cloud : Docker Hub et Maven Central limités (429, retries configurés dans `backend/gradle.properties`), ghcr/Oracle bloqués → images via `mirror.gcr.io/...` retaguées, miroir Maven Google dans `~/.gradle/init.d` (local, jamais commité), pas de build natif local (vérifié par la CI).
- springdoc : le customizer HATEOAS passe après les nôtres et remplace les schémas `Link`/`Links` (descriptions impossibles, exclus du test) ; un enum nullable ne peut pas être `nullable = true` (JSON Schema invalide) : le dire dans la description.
- Partie `metadata` de l’upload : lue brute (`episode/EpisodeMetadataReader`), acceptée sans type, `text/plain`, `application/octet-stream`, `application/json` ou `*+json` (outils type n8n/Zapier) ; JSON invalide → 400, validation → 422.
- Accessibilité de la SPA : boutons en attente en `aria-disabled` (jamais `disabled` : le focus tomberait sur `body`) ; formulaires d’édition recréés seulement si la ressource change (`{#key}` sur l’identité, jamais sur le contenu : le focus serait perdu), valeurs rechargées après succès ; focus déplacé sur un titre stable (`tabindex=-1`) après une suppression (`ConfirmButton.afterConfirm`) ; statut écrit après le déplacement du focus (`focusThenAnnounce`) ; un bouton qui disparaît (« Annuler l’envoi ») rend d’abord le focus au bouton d’envoi ; Playwright ne remonte aucune progression d’envoi sur une requête interceptée : `installControllableUploads` (`e2e/support.ts`) remplace XMLHttpRequest ; indicateur statique de `app.html` jusqu’au montage (premier chargement) ; Lighthouse ne voit ni le focus ni la largeur à 320 px : parcours Playwright + axe (`frontend/e2e/`).
- SvelteKit 3 : pas de `svelte.config.js` (config dans `vite.config.ts`) ; imports `#lib/*` (champ `imports` de package.json) avec extension explicite au lieu de `$lib` ; `resolve()` de `$app/paths` prend l’id de route avec groupe (`resolve('/(app)/podcasts')`).
- `@vitest/coverage-v8` a `vitest` en peer exact : toujours les monter ensemble (groupe Dependabot `vitest`).
- `engine-strict=true` : Node ≠ 24 ou npm ≠ 12.2.1 → `npm ci` échoue ; installer `npm install -g npm@12.2.1`.
- Spotless formate aussi les `*.gradle.kts` (ktlint) : lancer `spotlessApply` après toute modif du build.
- `github/codeql-action/init` et `analyze` doivent avoir la même version (sinon « configuration error » de CodeQL) : groupe Dependabot `codeql-action` dans `.github/dependabot.yml`, à monter ensemble à la main si deux PR séparées subsistent.
- Ports : 8080 (backend), 5173 (Vite), 5432 (base de dev) ; conflit fréquent avec un autre PostgreSQL/une autre app → libérer le port ou changer `BERGACAST_PORT`/`SPRING_DATASOURCE_URL`.
- `docker compose` exige un `.env` (`POSTGRES_PASSWORD`, `BERGACAST_JWT_SECRET` en `:?`) même pour démarrer seulement `db`. Volume PostgreSQL 18 monté sur `/var/lib/postgresql` (et non `/var/lib/postgresql/data`).
